## What Are Terraform Modules?

A **Terraform module** is a container for multiple resources that are used together. Every Terraform configuration is technically a module — the **root module**. You can create **child modules** to encapsulate and reuse infrastructure logic.

```
Root Module (main.tf)
        │
        └── module "ec2_instance" {
                source = "./modules/ec2_instance"
                ...
            }
                    │
                    ▼
        Child Module (./modules/ec2_instance/)
        ├── main.tf       ← resource definitions
        ├── variables.tf  ← input variable declarations
        └── outputs.tf    ← output value declarations
```

**Without modules:**

```
Project A: VPC + EC2 + SG + RDS (all in one main.tf — 500 lines)
Project B: same VPC + EC2 + SG + RDS (copy-paste — duplicate code)
```

**With modules:**

```
modules/ec2_instance/   ← write once
modules/networking/     ← write once
modules/database/       ← write once

Project A: calls modules
Project B: calls same modules ← reuse, no duplication
```

## Why Use Modules? — 7 Key Benefits

![modules.md — 7 benefits: Modularity, Reusability, Simplified Collaboration, Versioning and Maintenance, Abstraction, Testing and Validation, Documentation](<assets/Screenshot (497).png>)

**1. Modularity** — Break infrastructure into smaller, self-contained components. Each module handles a specific piece of functionality (an EC2 instance, a database, a network configuration), making it easier to manage and reason about.

**2. Reusability** — Create reusable templates for common infrastructure components. Instead of rewriting similar configurations for multiple projects, reuse modules across different Terraform projects — reducing duplication and promoting consistency.

**3. Simplified Collaboration** — Different team members can work on separate modules independently, then combine them to build complex infrastructure deployments. This division of labor reduces conflicts in the codebase.

**4. Versioning and Maintenance** — Modules can have their own versioning. When you update a module, you increment its version, and other projects can choose when to adopt the new version — preventing unexpected changes in existing deployments.

**5. Abstraction** — Modules hide the complexity of underlying resources. An EC2 instance module hides the details of security groups, subnets, and other configs, letting users focus on high-level parameters like instance type and AMI ID.

**6. Testing and Validation** — Modules can be individually tested and validated before being used in multiple projects — reducing the risk of errors propagating across infrastructure.

**7. Documentation** — Modules promote self-documentation. When you define variables, outputs, and resource dependencies within a module, it becomes clear how the module should be used.

## Building the Module — `modules/ec2_instance/`

### Module `main.tf` — Resource Definition

The module's `main.tf` defines the actual EC2 resource using input variables:

```hcl
provider "aws" {
  region = "us-east-1"
}

resource "aws_instance" "example" {
  ami                         = var.ami_value
  instance_type               = var.instance_type_value
  subnet_id                   = var.subnet_id_value
  associate_public_ip_address = true
}
```

**Key point:** The resource uses `var.*` for all environment-specific values — nothing is hardcoded. This makes the module reusable across different AMIs, instance types, and subnets.

| Attribute                     | Value Source              | Description                              |
| ----------------------------- | ------------------------- | ---------------------------------------- |
| `ami`                         | `var.ami_value`           | AMI ID passed in from root module        |
| `instance_type`               | `var.instance_type_value` | Instance size passed from root module    |
| `subnet_id`                   | `var.subnet_id_value`     | Subnet ID passed from root module        |
| `associate_public_ip_address` | `true` (hardcoded)        | Always assign a public IP in this module |

![modules/ec2_instance/main.tf — provider aws us-east-1, aws_instance example using var.ami_value/var.instance_type_value/var.subnet_id_value, associate_public_ip_address true](<assets/Screenshot (487).png>)

### Module `variables.tf` — Input Declarations

The module declares three input variables — all required (no defaults), so the caller must supply them:

```hcl
variable "ami_value" {
  description = "value for the ami"
}

variable "instance_type_value" {
  description = "value for instance_type"
}

variable "subnet_id_value" {
  description = "value for the subnet_id"
}
```

**Why no defaults?** These values are environment-specific — the AMI ID, instance type, and subnet differ between environments (dev/staging/prod). Forcing the caller to provide them prevents accidental use of wrong values.

| Variable              | Description                  | Required |
| --------------------- | ---------------------------- | -------- |
| `ami_value`           | AMI ID for the EC2 instance  | ✅ Yes   |
| `instance_type_value` | EC2 instance type            | ✅ Yes   |
| `subnet_id_value`     | Subnet to launch instance in | ✅ Yes   |

![modules/ec2_instance/variables.tf — variable ami_value, instance_type_value, subnet_id_value all with descriptions only](<assets/Screenshot (488).png>)

---

### Module `outputs.tf` — Expose Public IP

The module exposes the EC2 instance's public IP address as an output so the root module (or other modules) can use it:

```hcl
output "public-ip-address" {
  value = aws_instance.example.public_ip
}
```

This output is accessible from the root module as:

```hcl
module.ec2_instance.public-ip-address
```

![modules/ec2_instance/outputs.tf — output public-ip-address, value = aws_instance.example.public_ip](<assets/Screenshot (489).png>)

## Root Module — `main.tf`

The root `main.tf` calls the `ec2_instance` module, passing in all required values:

```hcl
provider "aws" {
  region = "us-east-1"
}

module "ec2_instance" {
  source              = "./modules/ec2_instance"
  ami_value           = "ami-091138d0f0d41ff90"
  instance_type_value = "t2.micro"
  subnet_id_value     = "subnet-0d98cba5e69bd6e68"
}
```

**Breaking down the `module` block:**

| Argument              | Value                        | Purpose                                 |
| --------------------- | ---------------------------- | --------------------------------------- |
| `source`              | `"./modules/ec2_instance"`   | Path to the child module directory      |
| `ami_value`           | `"ami-091138d0f0d41ff90"`    | Passed to `var.ami_value` in the module |
| `instance_type_value` | `"t2.micro"`                 | Passed to `var.instance_type_value`     |
| `subnet_id_value`     | `"subnet-0d98cba5e69bd6e68"` | Passed to `var.subnet_id_value`         |

**How values flow through the module:**

```
Root main.tf
  module "ec2_instance" {
    ami_value = "ami-091138d0f0d41ff90"  ─────────────────┐
    instance_type_value = "t2.micro"    ──────────────┐   │
    subnet_id_value = "subnet-0d98..."  ──────────┐   │   │
  }                                               │   │   │
                                                  │   │   │
modules/ec2_instance/variables.tf                 │   │   │
  variable "subnet_id_value" ◄───────────────────┘   │   │
  variable "instance_type_value" ◄───────────────────┘   │
  variable "ami_value" ◄─────────────────────────────────┘
                    │
                    ▼
modules/ec2_instance/main.tf
  resource "aws_instance" "example" {
    ami           = var.ami_value           → "ami-091138d0f0d41ff90"
    instance_type = var.instance_type_value → "t2.micro"
    subnet_id     = var.subnet_id_value     → "subnet-0d98cba5e69bd6e68"
  }
                    │
                    ▼
modules/ec2_instance/outputs.tf
  output "public-ip-address" → aws_instance.example.public_ip
```

### Step 1 — `terraform init`

Initialize the working directory — Terraform downloads provider plugins and processes the module source.

```bash

Terraform has created a lock file .terraform.lock.hcl to record the provider
selections it made above. Include this file in your version control repository
so that Terraform can guarantee to make the same selections by default when
you run "terraform init" in the future.

Terraform has been successfully initialized!
```

**Important:** When using local modules, `terraform init` also processes the module directory — making the module available to the root configuration. After init, the explorer shows `.terraform/` and `.terraform.lock.hcl`.

## Module vs Root — Side-by-Side

| Aspect      | Root Module (`main.tf`)             | Child Module (`modules/ec2_instance/`) |
| ----------- | ----------------------------------- | -------------------------------------- |
| Purpose     | Orchestrates and calls modules      | Defines reusable infrastructure        |
| Variables   | Passes values to child modules      | Declares what inputs it accepts        |
| Outputs     | Can consume module outputs          | Exposes resource attributes            |
| Resources   | Usually none (delegates to modules) | Where actual resources are defined     |
| `source`    | Points to child module path         | N/A                                    |
| Reusability | Project-specific                    | Reusable across projects               |

## Module Resource Addressing

When a resource is inside a module, Terraform uses a namespaced address:

```
# Direct resource (no module):
aws_instance.example

# Resource inside a module:
module.ec2_instance.aws_instance.example
       │                │          │
       module keyword   module     resource name
                        name       in module
```

This means you can have two modules both containing `aws_instance.example` without conflict:

```
module.ec2_instance.aws_instance.example  ← EC2 module instance
module.database.aws_instance.bastion      ← DB module bastion host
```

## Key Concepts Covered

| Concept                        | Summary                                                                    |
| ------------------------------ | -------------------------------------------------------------------------- |
| **Module = container**         | A directory of `.tf` files treated as a reusable unit                      |
| **Root module**                | The top-level directory where `terraform apply` is run                     |
| **Child module**               | A subdirectory called via `module {}` block from the root                  |
| **`source`**                   | Path to the module — local (`./modules/x`) or remote (Terraform Registry)  |
| **Variable passing**           | Root passes values → child receives via `var.*`                            |
| **Output bubbling**            | Child exposes outputs → root accesses via `module.<name>.<output>`         |
| **Resource namespacing**       | `module.<name>.<type>.<name>` — full address of any resource in a module   |
| **`associate_public_ip`**      | Set `true` in module to ensure public IP is assigned on launch             |
| **No defaults in module**      | Force callers to supply all values — prevents wrong environment config     |
| **`terraform init` + modules** | Init processes module sources and downloads any remote module dependencies |
